# AI Agent 엔지니어링 개념 정리 (Step 1~30)

코드 문법이 아니라 **"왜 이렇게 만드는가"**에 집중한 개념 노트. 손으로 직접 돌려보고 실제로 확인한 것들 위주로 정리했다.

---

## 큰 그림: 이 30스텝이 어디로 가고 있는가

```
1~4    : LLM 호출의 기본 물리법칙 (상태 없음, 구조화 출력, 도구 호출)
5~9    : "모르는 걸 찾아서 답하기" — RAG
10~16  : 기억하기, 여러 방식으로 생각하기, 여러 에이전트로 나누기, 실시간으로 보여주기
17~19  : 안 죽는 에이전트 만들기 (방어, 평가, 관측)
20     : 1차 완성 (캡스톤)
21~29  : "생각하는 법"에서 "서비스로 만드는 법"으로 전환 (MCP, 승인, 비용, 프레임워크 비교, 보안, 배포)
30     : 2차 완성 (캡스톤)
```

**관통하는 원칙 하나**: LLM API는 상태가 없다(stateless). 이 사실 하나가 1번부터 30번까지 형태만 바꿔서 계속 반복된다 — 대화 기록을 다시 보내는 것도, tool 결과를 다시 넣는 것도, 그래프의 state가 노드 사이를 흘러다니는 것도 전부 "매번 통째로 다시 보여줘야 기억하는 것처럼 보인다"는 같은 원리다.

## Part 1. LLM 호출의 기본 물리법칙 (Step 1~2)

**Step 1 — LLM 호출 기초**
LLM API는 상태가 없다. "기억한다"는 건 모델의 능력이 아니라, 우리가 매번 전체 대화 기록을 다시 보내는 것뿐이다. temperature=0은 결정론적(같은 입력→같은 출력), 높을수록 매번 달라진다. 대화가 길어지면 토큰이 넘치므로 오래된 대화부터 잘라내는 슬라이딩 윈도우가 필요하다 — **잘리는 건 항상 가장 오래된 것**이지 최근 것이 아니다.

**Step 2 — 구조화된 출력**
"JSON으로만 답해"라는 프롬프트만으로는 부족하다: (1) 가끔 JSON 문법 자체가 깨지고, (2) 문법은 맞아도 값이 이상할 수 있다(`"category": "발주|재고|납기|기타"`처럼 여러 개를 뭉개서 답함). **"파싱 성공"과 "값이 맞음"은 서로 다른 검증**이다 — JSON Schema로 형식을 강제하고, Pydantic으로 값까지 검증해야 안전하다. 더 미묘한 포인트: **필드를 선언한 순서 = 모델이 토큰을 생성하는 순서**다. LLM은 이미 뱉은 토큰을 보며 다음 토큰을 만들기(autoregressive) 때문에, `reason`을 `category`보다 먼저 두면 "생각한 뒤 결론"이 되고, 나중에 두면 "결론부터 정하고 사후 합리화"가 된다 — 스키마 설계는 검증 도구일 뿐 아니라 모델의 사고 순서를 설계하는 레버다.

## Part 2. 에이전트의 시작 — Tool Calling (Step 3~4)

**Step 3 — Tool Calling 기초**
LLM은 함수를 절대 직접 실행하지 못한다. `tools`로 함수 명세(이름/설명/파라미터)를 알려주면, LLM은 "이 함수를 이 인자로 불러줘"라는 **구조화된 제안(tool_calls)**만 돌려준다. 실제 실행은 100% 우리 코드의 몫. 흐름은 항상 2단계 호출: 1차(제안) → 우리 코드가 실행 → 2차(결과를 보고 최종 답변). 도구가 여러 개일 때 "어떤 걸 쓸지/아예 안 쓸지"는 오직 `description` 텍스트를 보고 모델이 스스로 판단한다 — 라우팅 정확도는 코드 로직이 아니라 description 문구 품질에 달려있다. **흥미로운 함정**: `tools`가 요청에 들어있다는 사실 자체가 모델을 "이 도구 범위 안에서만 답해야 한다"고 스스로 좁혀서 판단하게 만든다(tool-anchoring) — system 프롬프트에 아무 말 안 해도 무관한 질문을 거부하는 이유가 이것.

**Step 4 — Agent Loop**
질문 하나가 도구 하나로 안 끝날 수 있다 — 여러 스텝에 걸쳐 도구를 반복 호출하는 루프가 필요하고, `max_steps`로 무한 루프를 막는다. 실무 함정: 지원 안 하는 요청(예: "재고 제일 적은 거 찾아줘" — 목록 조회 기능이 없음)을 만나면 모델이 가짜 인자를 지어내 호출했다가 실패하고, 답할 수 있었던 나머지 절반까지 통째로 포기하기도 한다 → system 프롬프트에 "지원 안 하는 요청은 이렇게 안내하라"를 명시해야 한다. **작은 로컬 모델은 멀티스텝 tool calling에서 비결정적으로 무너질 수 있다** — 같은 질문을 여러 번 돌리면 답변이 매번 다르고, 가끔 완전히 다른 언어(중국어 등)로 새기도 한다. `finish_reason=="stop"`이라고 안심하면 안 되고, `content`에 tool_call 형식이 그대로 새어나온 건 아닌지 검증하는 방어 로직이 실무에선 필수다.

## Part 3. 검색으로 지식을 확장하기 — RAG (Step 5~9)

**Step 5 — Embedding**
임베딩 = 텍스트를 벡터로 바꾸는 것. 코사인 유사도를 쓰는 이유는 선택이 아니라 필연이다 — 벡터 내적의 정의 자체에서 바로 나오고, 모든 차원에서 계산 가능하며, sin/tan은 애초에 유사도 지표로 못 쓴다(0°=180°를 구분 못하거나 90°에서 발산). **임베딩은 "판단"이 아니라 학습 시점에 이미 얼려진(frozen) 결과를 재생하는 것**이라, 실시간 system 프롬프트로 교정할 수 없다 — embeddings API엔 애초에 messages/role 구조가 없다. 임베딩은 표면적 단어 유사성만 보고 도메인 인과관계("재고 부족의 원인=납기 지연")는 모른다 → 이걸 고치려면 **후보를 넉넉히 추린 뒤(retrieve), 그 소수만 LLM에게 다시 판단시키는(rerank) 2단계 구조**가 필요하다. 단, **TOP_K를 너무 작게 잡으면 진짜 정답이 1차 필터에서 아예 탈락**해서 2차 LLM이 아무리 똑똑해도 못 살린다 — 이게 rerank보다 recall(놓치지 않기)이 더 근본적인 이유. 중요한 개념 정정: RAG에서 임베딩해서 저장해두는 건 **"질문들"이 아니라 "정보/지식(문서)"**이어야 한다 — 질문끼리 비교하는 건 FAQ/티켓 라우팅 같은 다른 용도.

**Step 6 — RAG 기초 (직접 구현)**
RAG = Retrieve(검색) + Augment(프롬프트에 끼워넣기) + Generate(생성). 프레임워크 없이 순수 코드로 만들어보면 뼈대가 뭔지 명확해진다. 핵심 안전장치: "규정에 없으면 모른다고 답하라"는 지시로 hallucination을 막는다. **RAG의 근본적 한계**: 검색(retrieve)은 정확해도 그 정보를 가지고 하는 추론(예: "400 < 500" 숫자 비교)은 모델이 틀릴 수 있다 — **"검색 정확도"와 "추론 정확도"는 완전히 다른 문제**이고, RAG는 전자만 고쳐준다. 후자는 가드레일(step17)이나 평가(step18)로 따로 잡아야 한다.

**Step 7 — 벡터DB (ChromaDB)**
메모리 리스트를 실제 벡터DB로 옮기면 영속성 + 대량 검색 + 메타데이터 필터(`where`)가 생긴다. **`where` 필터의 진짜 가치는 편의성이 아니다**: "먼저 top_k로 자르고 나서 Python에서 필터링"하면, 조건에 맞는 진짜 정답이 top_k 밖에 있어서 결과가 0개가 될 수 있다(실측으로 확인됨). `where`는 반대 순서(먼저 필터 → 그 안에서 top_k)로 동작해서 이 recall 함정을 원천 차단한다 — step5의 TOP_K 문제와 완전히 같은 구조다. 실전 팁: ChromaDB는 `hnsw:space`를 안 정해주면 기본값으로 코사인이 아니라 L2(유클리드) 거리를 쓴다 — 다만 벡터가 이미 정규화(크기=1)돼 있으면 L2와 코사인은 수학적으로 같은 순위를 낸다(그냥 눈금만 다름).

**Step 8 — 검색 품질 향상**
BM25(키워드 검색)는 "단어가 겹치는가"만 보고 의미는 모른다 — 그래서 품목 코드 같은 정확 일치엔 강하지만 패러프레이즈엔 취약하다(임베딩의 정반대 특성). 하이브리드 검색(`alpha`로 BM25+임베딩 가중합)이 둘의 장점을 섞는다. **중요한 구조 문제**: "임베딩으로 추리고 → LLM이 재정렬"만으로는 안 된다 — 이건 BM25를 전혀 안 쓰는 거라, 키워드가 정확히 겹치는 문서를 놓칠 수 있다. 진짜 완성형은 **하이브리드 검색(1단계) → LLM rerank(2단계)**를 이어붙이는 것 — "싼 방법 두 개(키워드+의미)로 넓게 훑고, 비싼 방법(LLM)은 그 소수에만 쓴다"가 실무 표준 패턴.

**Step 9 — Agent + RAG 결합**
RAG 검색도 그냥 하나의 tool이다(`search_policy`) — LLM 입장에서 "실시간 DB 조회"와 "문서 검색"은 구조적으로 다르지 않고, description만 보고 스스로 판단한다. 도구가 실제로 쓰이면 LLM 호출은 정확히 2번(1차: 도구 제안만 얻음, 사이에 실제 검색 실행, 2차: 진짜 최종 답변을 얻음) — 도구가 애초에 필요 없으면 1번으로 끝난다.

## Part 4. 기억하기 & 여러 방식으로 생각하기 (Step 10~11)

**Step 10 — 메모리**
단기 메모리: 대화가 길어지면 오래된 부분을 요약으로 압축(핵심 사실은 남아야 함). 장기 메모리: 과거 대화를 벡터로 저장해뒀다가 관련 있을 때만 꺼내온다(관련 없으면 억지로 안 끌어옴). 단 step10_2는 저장소를 메모리 내 리스트로 두어 "검색 원리"만 보여주는 데모이며, 실제로 세션을 넘어 유지하려면 DB 같은 영속 저장소가 필요하다. 작은 모델은 요약 과정에서 언어가 새기도 해서(한국어→중국어) 프롬프트에 언어를 명시적으로 고정해야 한다.

**Step 11 — 추론 패턴 (ReAct vs Plan-and-Execute)**
"상황 봐서 아무거나 골라 쓰라"는 게 아니라, **완전히 다른 두 구조**다. ReAct는 하나의 이어지는 대화 안에서 매 스텝 "지금까지 알아낸 것"을 실제로 보며 다음 행동을 즉흥적으로 정한다. Plan-and-Execute는 (1) 계획을 실행 전에 전부 세우고, (2) 각 하위 작업을 **완전히 독립된 새 대화**로 실행하고, (3) 마지막에 종합한다. **직접 재현한 실패 사례**: "재고가 500kg 미만이면 납기를 확인해줘" 같은 조건부 작업을 Plan-and-Execute로 시키면, 계획 단계에서 "조건이 만족되면 확인" 이라고 써놓고도, 실제 실행 단계는 앞 단계 결과를 전혀 모르는 독립 대화라서 조건을 무시하고 무조건 확인해버린다. → **작업에 단계 간 의존성/조건이 있으면 ReAct, 하위 작업들이 서로 독립적이면 Plan-and-Execute**를 설계 시점에 선택해야 한다.

## Part 5. 여러 에이전트, 그래프로 표현하기 (Step 12~14)

**Step 12 — 멀티 에이전트 (Supervisor)**
도구를 다 몰아넣은 에이전트 하나 대신, 역할별 전문가 + 라우팅하는 supervisor로 나눈다. 실전 교훈: 라우팅을 "필요한 걸 리스트로 골라봐"라고 물으면 모델이 거의 항상 다 고른다 — "재고 필요해?", "납기 필요해?"처럼 **각각 독립된 boolean으로 따로 물어보는 게 작은 모델엔 훨씬 정확**하다.

**Step 13 — 그래프 오케스트레이션 (직접 구현)**
"그래프 AI"의 정체는 단순하다: **상태(state, 그냥 dict) + 노드(state를 받아 state를 돌려주는 함수) + 엣지(다음 노드를 정하는 규칙)**. `add_edge`는 "다음 노드가 무조건 고정"인 경우, `add_conditional_edge`는 "상태를 봐야 다음 노드가 정해지는"(if/elif와 동급) 경우에 쓴다. 그래프는 일직선이 아니라 되돌아갈 수 있다(순환) — 이게 tool 호출 루프나 ReAct 반복을 그래프로 표현하게 해준다. **중요한 설계 구분**: 그래프의 **구조(어떤 노드가 있고 어떻게 연결되는지)는 사람이 코드로 미리 고정**해두고, AI는 그 안의 갈림길에서 "이미 준비된 선택지 중 하나를 고르는" 역할만 한다 — AI가 워크플로우 자체를 즉석에서 만들어내는 게 아니다. (참고: `class Graph`는 그 자체로 실행되는 게 아니라 설계도일 뿐이고, 실제 동작은 `g = Graph()`로 인스턴스를 만들고 그 메서드를 호출할 때 일어난다 — `Graph.run()`의 for 루프가 실제로 `check`/`halve` 같은 노드 함수들을 호출해준다.)

**Step 14 — LangGraph**
Step 13에서 직접 만든 엔진을 실제 LangGraph로 재구현 — `StateGraph`/`add_conditional_edges`가 직접 만든 것과 거의 1:1 대응된다. `create_agent` 한 줄이 step4에서 손으로 짠 tool-calling 루프 전체를 대신해준다.

## Part 6. 자율성과 실시간성 (Step 15~16)

**Step 15 — 자율 루프 & Reflection**
Self-reflection: 답을 바로 확정 않고 스스로 비평 후 개선 — "고칠 게 없다"는 판단도 정상적인 결과다. 자율 루프: 목표만 주어지면 스스로 다음 행동과 종료 시점을 정한다. 모델이 시킨 대로 완벽하게 행동하지 않을 수 있으므로(스스로 종료 신호를 안 부르고 그냥 텍스트로 끝내버리는 경우) `max_steps` 같은 강제 종료 안전장치가 항상 필요하다.

**Step 16 — 스트리밍**
전체 완료를 기다리지 않고 토큰이 생성되는 즉시 조각으로 받는다 — 총 소요 시간은 비슷해도 "체감 속도"가 완전히 다르다(챗봇 UI의 "타이핑 중" 효과). tool_calls도 이름/인자가 조각조각 나눠서 오므로 `index`로 이어붙이는 로직이 필요하다.

## Part 7. 안 죽는 에이전트 만들기 (Step 17~19)

**Step 17 — 가드레일 & 견고성**
입력 검증은 2겹이 필요하다: "이전 지시 무시해" 같은 직접 명령은 규칙 기반으로 즉시 차단되지만, "DAN 역할극" 같은 우회는 LLM 판단까지 가야 걸린다. 출력 필터링(PII 마스킹, 시스템 프롬프트 유출 차단)과 재시도(지수 백오프)까지 갖춰야 프로덕션에서 안 죽는다.

**Step 18 — 평가 (Evaluation)**
정답이 하나로 안 정해지는 자유 서술형 답변을, LLM을 "심사위원"으로 써서 자동 채점한다(표현이 달라도 핵심 사실이 맞으면 pass). **실전 교훈**: `reasoning`/`verdict`/`score`를 동시에 물으면 reasoning/verdict와 score가 서로 어긋나는 자기모순(예: 근거는 맞다는데 1점)이 나온다 — **LLM에게 여러 판단을 동시에 시키면 서로 어긋날 수 있다**. 그래서 `score`를 없애고 reasoning+verdict만 남겼더니 일관성이 생겼다. 또 step18_2에는 일부러 틀린 기준을 준 대조군 케이스가 있어서, 정상 결과는 5/5가 아니라 4/5다.

**Step 19 — Observability**
함수 호출마다 입력/출력/소요시간을 자동 기록(tracing)하고, 지연시간의 p50/p95를 집계(metrics)한다. **평균만 보면 "가끔 오래 걸리는 요청"을 놓친다** — percentile이 이걸 잡아낸다. 로컬 모델은 토큰이 공짜지만, 비용 계산식은 유료 API로 바꾸는 순간 그대로 실전에 쓰인다.

## Part 8. 1차 완성 — 캡스톤 (Step 20)

Step 6~19의 조각(RAG, 메모리, 그래프, 가드레일, 추적)을 **그래프 하나**로 합친 첫 완성형 에이전트. `input_guard → classify → (전문 노드) → respond → output_guard` 경로를 질문마다 다르게 탄다. 여기서 만든 파일은 Step 29(서빙), Step 30(캡스톤 v2)에서 그대로 재사용된다 — **Step 13에서 그래프 뼈대를 제대로 이해해뒀으면 여기가 훨씬 수월**해진다.

## Part 9. "생각하는 법"에서 "서비스로 만드는 법"으로 (Step 21~29)

> 여기부터는 초점이 바뀐다: 에이전트 내부 동작 원리가 아니라, 그걸 실제 백엔드 서비스로 만들 때 마주치는 문제들.

**Step 21 — MCP 기초**
지금까지 tool은 파이썬 dict로 코드에 직접 박아넣었다. MCP(Model Context Protocol)는 tool 정의+실행을 별도 서버 프로세스로 분리하는 표준 — 클라이언트는 `list_tools()`로 스키마를 자동으로 받아오고, 직접 스키마를 안 써도 된다. MCP는 새로운 프로그래밍 방식이 아니라, 이미 알던 평범한 함수를 "노출하는 방식"일 뿐이다.

**Step 22 — MCP + Agent 통합**
에이전트가 tool 목록을 코드에 하드코딩하지 않고 MCP 서버에게 통째로 위임한다 — 서버에 tool을 하나 추가하면, 에이전트 코드를 한 줄도 안 고쳐도 새 도구를 자동으로 쓸 수 있다. 이게 MCP의 핵심 가치.

**Step 23 — Human-in-the-loop**
조회 도구는 잘못 불러도 되돌리기 쉽지만, 실제 발주 같은 되돌리기 어려운 도구는 실행 전 사람 승인이 필요하다. `input()` 방식은 그 자리에서 프로세스를 블로킹하지만, LangGraph의 `interrupt()`는 실행 자체를 완전히 멈췄다가 나중에 재개할 수 있다(이 스텝 코드는 `InMemorySaver`라서 같은 프로세스 안에서만 재개된다 — 다른 서버/프로세스에서 재개하려면 영속 checkpointer가 필요하다). 실제 슬랙 승인 봇 같은 걸 만들려면 후자 방식에 영속 저장소를 더해야 한다.

**Step 24 — 프롬프트 캐싱**
반복되는 긴 접두사(시스템 프롬프트 등)를 앞에 고정 배치하면 재계산을 줄일 수 있다. 원칙: **안 바뀌는 긴 내용은 앞, 매번 바뀌는 질문은 뒤** — 순서를 반대로 하면 캐싱 효과가 아예 없다. 로컬 모델의 캐싱은 감지 기반이라 불안정할 수 있지만, 클라우드 API의 `cache_control`은 명시적이고 보장된다.

**Step 25 — 비용 기반 모델 라우팅**
쉬운 질문은 작은/싼 모델, 어려운 질문은 큰/비싼 모델로. **실전에서 겪은 진짜 문제**: 작은 모델에게 "이 질문이 복잡한지" 스스로 판단시키면, 질문 내용과 무관하게 거의 항상 "복잡함"이라고 답한다 — **작은 모델일수록 "분류/판단" 자체를 못 하는 경우가 흔하다**. 그래서 판단 자체를 regex/키워드 기반 규칙으로 바꿔야 했다.

**Step 26 — 컨텍스트 압축**
대화가 길어질 때 실제로 커지는 건 대화 턴이 아니라 tool 호출 결과다. 오래된 tool 결과를 한 줄 요약으로 압축하면, 원문이 사라져도 핵심 사실은 남는다. (실전 버그: `messages`에 우리가 만든 dict와 SDK가 준 객체가 섞여 있어서 `m["role"]`로 통일해서 접근하면 에러 — 이건 step3_2에서 배운 "메시지에 pydantic 객체를 그대로 넣어도 된다"는 사실의 반대편 함정이다.)

**Step 27 — 프레임워크 비교 (AutoGen vs 직접 구현)**
직접 짠 supervisor(코드로 라우팅 확정)와 AutoGen의 `SelectorGroupChat`(매 턴 LLM에게 "다음 화자"를 직접 물음)을 비교 — **AI가 라우팅까지 맡으면 더 유연해지지만 덜 예측 가능해진다**(실행마다 결과가 달라짐, 이건 버그가 아니라 관찰 대상).

**Step 28 — 보안 레드티밍**
Step 17 가드레일을 공격자 입장에서 직접 깨본다 — 규칙 레이어(BLOCKLIST)의 우회는 예상되는 결과다(띄어쓰기로 쪼갠 "우회 표기"는 규칙 레이어를 확실히 피한다). "역할극 탈옥"과 "권위 사칭"도 규칙 레이어는 통과하지만 LLM 레이어가 잡아낼지는 실행해서 관찰할 일이다. 통과가 나오면 버그가 아니라 레드티밍이 구멍을 찾은 것이다. **가드레일은 한 번 만들고 끝이 아니라, 공격→수정→재검증을 반복하는 것.**

**Step 29 — FastAPI 서빙 + 배포**
Step 20 에이전트를 HTTP API로 감싸고 Docker로 배포 가능하게 만든다 — `POST /chat`은 에이전트 로직을 새로 안 짜고 `ask()`를 그대로 가져다 쓴다(로직과 서빙 레이어 분리; 단 `/chat/stream`은 답변 생성 프롬프트를 인라인으로 다시 구성하고 `/metrics`에도 집계되지 않는다). Docker 안에서 `localhost`는 호스트를 안 가리킨다는 실전 이슈(`host.docker.internal`)까지 포함. **step16의 터미널 스트리밍을 브라우저까지 이으려면 SSE(Server-Sent Events)가 필요**하다 — `/chat/stream` 엔드포인트로 실제 구현: 그래프의 마지막 노드(문장을 만드는 respond_node)만 `stream=True`로 바꿔 토큰 단위로 내보낸다. 여기서 드러나는 근본적 긴장: **output_guard는 "완성된 문장 전체"를 봐야 판단할 수 있는데, 그 문장은 이미 토큰 단위로 다 스트리밍된 뒤**다 — 실시간 스트리밍과 "보내기 전 전체 검사"는 동시에 완벽히 만족될 수 없고, 실무에서는 (a) 버퍼링 후 통과한 것만 보내거나 (b) 일단 보내고 위반 시 정정 이벤트를 추가로 보내는 것 중 하나를 선택해야 한다.

## Part 10. 최종 완성 — 캡스톤 v2 (Step 30)

Step 20에 MCP 기반 tool 실행 + human-in-the-loop 승인 게이트를 더한, 가장 실제 서비스에 가까운 형태. 핵심 교훈: MCP 서버 입장에서 `place_order`는 `check_stock`과 다를 바 없는 평범한 tool이다 — **"이 도구는 위험하다"는 판단은 서버가 아니라 그걸 호출하는 클라이언트 쪽의 책임**이다. 실제 서비스로 만들려면 `input()` 승인 대신 별도 엔드포인트나 `interrupt()` 패턴으로 바꿔야 한다(블로킹 금지).

## 자주 반복되는 핵심 메타 개념 (전체를 관통하는 것들)

1. **Stateless**: 모델은 아무것도 기억 안 한다. "기억"은 항상 우리가 매번 다시 보내는 데이터의 결과다.
2. **검색 정확도 ≠ 추론 정확도**: RAG/도구가 맞는 정보를 가져와도, 그걸로 하는 계산/논리는 모델이 틀릴 수 있다. 서로 다른 문제, 서로 다른 해법(가드레일/평가).
3. **작은 로컬 모델의 한계**: 분류/판단을 스스로 시키면 신뢰도가 낮다(step25), 멀티스텝에서 비결정적으로 무너진다(step4), 여러 판단을 동시에 시키면 자기모순이 난다(step18). 실무에선 판단을 규칙 기반으로 대체하거나, 필드를 쪼개서 물어야 한다.
4. **비용/난이도 스펙트럼**: ① 프롬프트로 되면 제일 쌈 → ② 파이프라인/구조로 보완(RAG, rerank, 하이브리드 검색) → ③ 파인튜닝(제일 비쌈, 중소규모는 거의 안 씀).
5. **구조(누가 설계) vs 판단(누가 결정)**: 그래프의 노드/엣지, 승인이 필요한 tool 목록, 어떤 도구를 노출할지 — 이런 "틀"은 항상 사람이 코드로 미리 정해두고, AI는 그 틀 안에서만 판단한다.
6. **안전장치는 항상 필요하다**: `max_steps`(무한루프), 가드레일(입력/출력), 재시도(일시 장애), 레드티밍(방어 반복 검증) — AI가 "시킨 대로 완벽하게" 행동한다고 가정하면 안 된다.
